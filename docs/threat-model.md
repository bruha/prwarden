# Threat model

What this reviewer assumes about the things it reads, runs, and writes to, and what
stops each of them from doing harm. Written after reading the code, not from the
design intent: every mitigation below names where it is enforced.

The comparable document in Alibaba's reviewer is `ASSURANCE_CASE.md`, and this one
follows its shape deliberately so the two can be read side by side.

## What the system does

1. Asks GitHub, through the authenticated `gh` CLI, which pull requests are open.
2. Fetches each reviewed head into a detached worktree from a local checkout.
3. Builds a prompt from the diff, prior review comments, GitHub checks, and, from
   the base branch, its `.prwarden/background.md`, the "Code review" rules in its
   agent instruction files, and its recent commit messages on the changed files.
4. Runs an authenticated coding-agent CLI, in that worktree, with the prompt.
5. Validates every citation in the response against the worktree.
6. Posts inline comments, a review, an approval, or advisory pull-request comments
   through `gh`, or sends a Slack message through an incoming webhook.
7. Records what it delivered in a local JSON state file.

## Actors and trust

| Actor | Trust | Why |
| --- | --- | --- |
| Operator | Trusted | Owns `.env`, `repositories.json`, `reviews.json`, and the schedule |
| Local checkout | Trusted as a Git object source | Its working tree is never used; only objects are |
| Base branch | Trusted for its code review rules, its background note, and its `linguist-generated` marks | Merged by the maintainers; the pull request under review cannot change it, and a pull request that changes them for later reviews is never approved until a person with write access other than its author signs it off |
| Reviewed head | **Untrusted** | Any contributor can put anything in a diff |
| Coding-agent CLI | Semi-trusted | Authenticated by the operator, but it is a general tool with its own capabilities and its own sandbox |
| Model response | **Untrusted** | Validated in full before anything is delivered |
| GitHub API via `gh` | Semi-trusted | Data shapes are validated; the binary is the operator's |
| Linked issues and Jira work items | **Untrusted** | Anyone who can edit an issue wrote it; read through `gh` and the operator's `acli`, whose sign-in PR Warden never stores: `prwarden setup --jira` hands a pasted API token to `acli` on standard input and keeps no copy |
| Slack webhook | Write-only sink | Never read from; the URL is a secret |
| State file | Trusted | Local, atomic, lock-guarded |

The boundary that matters most is the third one. Everything in the reviewed head —
code, file names, commit messages, the pull-request body, and prior comments — is
data written by whoever opened the pull request.

## Threats and what stops them

| # | Threat | Mitigation, and where |
| --- | --- | --- |
| T1 | Command injection through diff, path, branch, or model-supplied text | No shell anywhere: every command a review starts goes through `run_cmd_streams` in `prwarden/commands.py`, always with an argument list, `check=False`, an explicit timeout, and a controlled environment; the few other `subprocess.run` calls, in the tool checks, setup's installers and sign-ins, the release tool, and the public-safety hooks, take argument lists too. `shell=True`, `os.system`, and `os.popen` appear zero times in `prwarden/`. The prompt, which carries untrusted diff text, is passed as one argv element, never interpolated into a command string |
| T2 | Prompt injection from the reviewed head, making the agent act rather than review | Every prompt names the untrusted inputs and forbids following instructions in them (`prwarden/engine.py`), forbids edits, commands, network, browsing, and host skills or subagents, and the engine's own sandbox enforces it independently — observed in production [pr:7nzi], where Antigravity refused a `ListDir` call the review had asked for. Data cannot end the block it was placed in: `contain_untrusted` neutralises the prompt's own tag names inside every untrusted value, so a pull-request body carrying `</pr-body>` cannot continue as the prompt's own voice. Code review rules, which the prompt treats as requirements, are read from the base branch, never from the reviewed head, so a pull request cannot add a rule that excuses it; a rule may only add requirements, and a finding's quoted rule must be the base branch's own text. The base branch's commit messages on the changed files are merged but written by whoever committed, so they are contained like the background note and framed as messages, never code or instructions; `git log` reads them from the base tip's objects with each path after `--`. Codex has no file tool and reads with shell commands, so its prompt allows commands that only read, inside the workspace, and forbids running anything else, the head's own scripts included; its read-only, no-network sandbox enforces what that wording cannot, and an answer it gives without a successful command that raises no finding and confirms no candidate is refused, so a Codex review that read nothing cannot approve, settle a level, or discard the candidates it was asked to verify. Kiro and Antigravity load the head's own instruction files, such as `AGENTS.md`, into the model's context as instructions and cannot be told not to, so their prompts name each such file the head carries as untrusted data; an instruction planted there was obeyed without that notice and ignored with it. The issues a pull request links, GitHub's and Jira's, are contained the same way in a `linked-issues` block and framed as untrusted context that never relaxes a rule. Text in any of it that speaks to the reviewer or vouches for the change, such as "ignore this secret", argues for an omission rather than giving an instruction, so every prompt names it as a claim to check and never a reason to omit a finding or approve; a committed credential with a distinctive shape is found by `secret_scan` (`prwarden/secret_scan.py`) without a model, so no such text can talk the review out of reporting it or into approving it. Residual risk is real and documented below |
| T3 | Secret leakage to the agent CLI | The engine environment is built from an allowlist, not inherited: `build_engine_environment` (`prwarden/engine.py`) passes `HOME`, `PATH`, `TMPDIR`, `TEMP`, `TMP`, `LANG`, `LC_ALL`, `USER`, `LOGNAME`, `SHELL` and nothing else, and the call site sets `inherit_environment=False`. `SLACK_WEBHOOK_URL` and the rest of `.env` are therefore not visible to the model's process. The reviewer's pinned GitHub token, and the token of any account a repository entry names with `github_account`, is held in `prwarden/github.py` and added only to that module's `gh` calls, never to `os.environ`, so no engine allowlist can forward it. `refresh-terms` passes such a token in its `gh` child's environment, never in its arguments, which every process on the machine can read. The environment is not the only place a secret lives: the engine runs as the operator, whose home folder holds keys and logins, and with the settings each CLI had before, Claude, Kiro, and Codex each read a file planted there. Each adapter therefore confines its engine to the review worktree and the dependency directories linked into it (`dependency_read_targets`): Claude runs in `dontAsk` permission mode with each dependency directory added by `--add-dir`, Kiro runs untrusted with its agent's reads allowed only under `./**`, Codex runs under a permission profile that reads the workspace, those directories, and the minimal paths its tools need, with no network, and Codex older than 0.138.0, which would ignore the profile, is refused. Antigravity already reads only the worktrees root and those directories. With these settings the same planted file stayed unread by every engine, and the worktree and its dependencies stayed readable |
| T4 | Secret or local-path leakage into Slack or GitHub | The webhook is read from the environment and never printed; Slack message bodies pass through `redact_local_paths` (`prwarden/delivery.py`) so a machine path in a finding cannot reach a channel. A credential the reviewed change commits is named by its kind and shown only by its fixed prefix in every finding PR Warden posts, a model's quoted excerpt included, and the prompts forbid copying one into any field, so a comment does not keep a value a later force-push removed. Whatever a model wrote, every comment, review, approval text, and Slack message is checked just before it is sent (`guard_outgoing`, `prwarden/delivery.py`): text holding a credential-shaped value, private key material, or a value this host holds (its GitHub tokens, its webhook, and every variable an engine may see) is never sent, and the head is recorded `delivery_blocked`, so a model talked into reading a key from the host cannot post it to the pull request's author. A value disguised as something else, such as split or encoded, is not caught; only keeping the engine away from the host's secrets stops that. A webhook belongs to one workspace, so a repository configured with `"slack": false` is never named in it: its owner's pull requests are reviewed on GitHub, and its run errors and notices stay in the run log. `.env` and `repositories.json` are untracked, and the setup instructions create `.env` mode 600. `prwarden setup` reads a pasted webhook without echoing it, never prints it, and writes it only to `.env`, mode 600 |
| T5 | Path traversal through a model-supplied citation path | `_required_evidence` (`prwarden/review.py`) rejects absolute paths, resolves the candidate, and requires it to sit inside the worktree or an allowed dependency root; resolution happens before the comparison, so a symlink cannot escape. A path that does not exist in the reviewed head is rejected outright |
| T6 | A fabricated or drifted finding reaching a pull request | The anchor must be an added line of the diff; every citation's excerpt must be that line's exact text; the whole response is rejected and retried once with the reason otherwise; a separate adversarial pass judges each candidate by reference, so it can neither restate nor re-anchor what it confirms. A finding whose position cannot be established is dropped, never posted with a guess |
| T7 | Duplicate or contradictory delivery after a retry | GitHub writes are never blindly retried, delivery revalidates mutable pull-request state first, and every terminal outcome is recorded per (repository, pull request, head, destination) in an atomically written state file guarded by a process lock (`prwarden/state.py`) |
| T8 | Two runs colliding on state | A live run takes the process lock and a second one exits 0 as a safe skip; dry runs take no lock and record no state. Each run appends its review history to a file of its own, which no other run writes, so the history needs no lock |
| T9 | A malformed or hostile GitHub response | Every field read from `gh` is type-checked before use; a record missing what a decision needs is treated as unknown and the safe branch is taken, for example a file with no provable changed-line count is deferred rather than assumed textless |
| T10 | Writing outside the intended places | A review run writes only under its state directory (`.state/` in a checkout, `~/.local/state/prwarden` when installed: state, run logs, review history, worktrees) and into the clones it manages itself, and never to the reviewed repository or beside an installed package. A managed clone is fetched with GitHub CLI's token for its account through a credential helper set on the command line, with git's other helpers off, so the token is never stored. `prwarden setup` writes only the configuration directory and `prwarden schedule` only its own LaunchAgent or systemd units. Connecting Slack in setup opens Slack's own page for a new app in the browser, asking for the `incoming-webhook` scope alone, and sends one test message, naming no repository, to the webhook the operator pasted. Installing a missing tool runs a Homebrew formula or cask, or the vendor's own installer fetched from the vendor's domain, only after the operator has seen the command and said yes, and never with `sudo`; that installer is trusted exactly as far as it would be if the operator ran it by hand. Inside a review worktree it adds only Kiro's controller-owned settings file and read-only agent (T11), which are never committed or pushed. Applying fixes is deliberately not a feature |
| T11 | Agent host configuration shipped by the reviewed head | An agent CLI reads workspace configuration from the directory it starts in, which is the reviewed head, and some of it names commands the CLI runs itself, outside the tool permissions the review grants the model. Each case was confirmed with a head whose server, hook, or helper created a file. Kiro starts MCP servers from `.kiro/settings/mcp.json` and `.amazonq/mcp.json`; Antigravity starts MCP servers and hooks from `.agents/` and `.agent/`, plugins included, with its sandbox on. Neither CLI can be told to skip them, so `refuse_host_configuration` (`prwarden/engine.py`) refuses, before the CLI starts, a head whose configuration directories hold anything but documents (`.kiro/steering`, `.kiro/specs`, `.amazonq/rules`, `.agents/rules`, `.agents/workflows`) or a symlink, and Kiro gets the only configuration files it finds there: its settings and PR Warden's own agent, which offers the model no tool but reading and searching files, no MCP server, and no skill. That settings file also turns off Kiro's code intelligence, so no language server starts and loads the project's configuration. Kiro's `code` tool still writes `.kiro/settings/lsp.json` during a call, and the next call there refused the head, so the adapter removes that one file after every call; Kiro CLI 3.1 also creates `.kiro/agents`, which holds the controller's agent; a head that ships `lsp.json`, a link, or any agent but that exact file is refused before any call, and a refusal names the file it found. Claude Code's safe mode still loaded a head's `.claude/settings.json`, whose `apiKeyHelper` ran and whose `env` redirected the API requests, so the adapter reads only user settings and no MCP configuration. Codex loads a head's `.codex/config.toml` only for a project the user configuration trusts, and the adapter never reads the user configuration |
| T12 | An unread generated file hiding a change | GitHub omits the patch of a file whose diff is too large, and nothing local can read it, so its pull request is never approved, unless the path matches the reviews file's `diff.ignored_missing_patch`. Left out, that is the built-in list `DEFAULT_IGNORED_MISSING_PATCH_PATTERNS` (`prwarden/config.py`): dependency lockfiles, `*.tsbuildinfo`, and Wrangler's `worker-configuration.d.ts`, matched by name at any depth. A match is skipped only while GitHub omits its patch, so a change small enough to show is still reviewed. Images, minified bundles, source maps, test snapshots, and other generators' output are left out because each can hold a line worth reading. An operator's own list replaces the built-in one, and `[]` ignores nothing. A repository's own `linguist-generated` marks count as well, read with `git check-attr --source` from the base branch's tip (`read_generated_marks`, `prwarden/workspace.py`) and never from the head or the local working tree, so a pull request cannot mark its own file generated; an unmark only ever keeps a file unread, and marks that cannot be read leave every omitted file unread, a listed one included. A Git older than 2.40 cannot read attributes from a commit, so the marks are not read there and the list alone decides, as before. Residual: an unread lockfile can point a dependency at another source; a CI install that refuses a lockfile out of step with its manifest, such as `npm ci`, `bun install --frozen-lockfile`, or `cargo build --locked`, is what catches that |
| T13 | A pull request that reconfigures every later review, by loosening the code review rules, rewriting the background note, marking files generated, changing who must review, or removing a CI check | The rules, the background note, and the `linguist-generated` marks are read from the base branch, so a pull request cannot change its own review (T2, T12). A pull request that changes them for the reviews after it is never approved without a person: `review_policy_changes` (`prwarden/review.py`) names any changed file under `.prwarden/` or `.github/workflows/`, any `.gitattributes`, a `CODEOWNERS`, and an instruction file whose "Code review" sections differ from the base branch's, and a clean result is then withheld and recorded until a person signs that head off. `policy_signoff` (`prwarden/github.py`) counts only an approval of the exact head, or an `LGTM` written after the controller withheld it, by a person with write access who is not the author and not a bot, in a comment this tool did not write; a permission or a list it cannot read counts as no sign-off, so an author cannot sign off their own change and an outsider cannot sign off anybody's. Its findings still post. Residual: a person with write access who signs off a change is trusted with it, as GitHub trusts them to merge it; only GitHub's own settings stop a person with merge rights from merging such a change, and a ruleset that requires a code owner's review of these paths is the repository owner's control, not this tool's |
| T14 | Reviewed text reaching another reader through the review history | The history holds pull-request titles and finding text, which the reviewed project and a model wrote. Its files are created mode `0600`, and `prwarden history` (`prwarden/history.py`) prints every such value on one line with control characters replaced, so a title cannot carry a terminal escape sequence to the reader. No decision of this tool reads the history back, so nothing in it can steer a later review. Residual: an agent told to run `prwarden history` reads that text as input, and only its own instructions keep it data; the README's suggested instruction says so |
| T15 | A failed check's log steering the checks level, or reaching the pull request | The log was printed by code the pull request runs. It is read only for a review that found nothing and would approve but for its checks, or that approves beside failed checks GitHub does not require, cut to the failing step and at most 120 lines, has credential-shaped values replaced (`redact_credentials_in_text`, `prwarden/check_logs.py`), and reaches the prompt only inside a contained `check-logs` block that the prompt names as untrusted. The level cannot approve and has no verifier to persuade: the controller keeps a reading only when its quoted line is in that log and every workspace line it cites is in the head, and the note quotes log lines as code and breaks up mentions, so a log cannot make the comment notify anybody. A reading that fails is dropped and the note posts without it. Residual: the model's cause and fix are its own words, which a crafted log can still bend toward a misleading fix; the note says who read it and to check a fix before acting on it |
| T16 | A failing check passed off as one GitHub does not require, to get an approval | Which checks are required is read from GitHub, never from the pull request or a model: `check_requirements` (`prwarden/github.py`) asks for each check's `isRequired` on this pull request, which the base branch's protection and rulesets decide and only a repository admin can change. It is read after the checks themselves, and a failed check missing from the answer, a branch that requires no check, or an answer that cannot be read whole leaves every failed check holding the approval (`blocking_checks`, `prwarden/review.py`). Renaming a required job is a change under `.github/workflows/`, which needs a person's sign-off (T13). Residual: a check whose name an author can change without touching a workflow, such as one read from another file or reported by an external CI service, can step out from under its requirement; GitHub then still reports the required check as expected and blocks the merge, so the approval does not merge the change on its own |

## Residual risk, stated plainly

**The agent CLI is the weak point, and it cannot be fully mitigated from here.** It
runs with the operator's credentials in a directory full of untrusted content, and
what stops it acting on an instruction planted in that content is the prompt, its own
sandbox, and nothing else this project controls. Three things reduce the damage: it
is given no secrets (T3), the controller believes nothing it returns without checking
it against the worktree (T5, T6), and it can only ever cause a comment, an approval,
or a Slack message — never a code change or a merge.

The honest limit of that argument is that an approval is itself an action. A
successful injection that produced a clean verdict would spend the reviewer's
approval on a change nobody read. The rules that forbid approving drafts, conflicts,
partial reviews, and self-authored pull requests narrow this, and the second engine
verifying candidates narrows it further, but a clean review is the one outcome that
requires no evidence to be delivered.

## One hardening item this audit found

`pull_request.head_sha` reaches `git fetch origin <sha>`, `git cat-file`, and
`git worktree add` as an argv element, and is now validated as a Git object name at
the GitHub boundary instead: `validate_object_name` accepts 40 or 64 lowercase hex
characters and refuses everything else, applied where a pull request is discovered
and where its snapshot is read (`prwarden/github.py`). Git reads an object name as a
revision expression, so an unvalidated value would not merely fail to resolve —
`HEAD`, `main@{1}` and a path each mean something, and a leading `-` means an option.
Nothing has ever sent such a value; the guarantee was inherited from GitHub's API,
and this makes it local so the boundary holds on its own.

A second, smaller assumption: the prompt is delivered as a command-line argument, so
its size is bounded by the platform's argument limit. The reviews file's
`diff.max_bytes` defaults to 200 KB against roughly 1 MB available on macOS, so there
is headroom, but raising that setting far enough would fail as an exec error rather
than as a review error.

## Automated verification

| Check | Command | When |
| --- | --- | --- |
| Unit suite, 461 tests | `python3 -m unittest discover -s tests` | Every change, on 3.11 through 3.15 in CI |
| Oldest-interpreter compatibility | the same suite under `python3.11` | Syntax changes locally; CI covers 3.11 |
| Syntax | `python3 -m compileall -q prwarden tests` | Every change |
| Whitespace | `git diff --check` | Every change |
| Dependencies | none to scan: no third-party runtime dependencies | By construction |

The last row is a genuine advantage over a tool with a dependency tree: there is no
supply chain to monitor, because there is nothing installed to review with.
